# airlok

airlok собирает проект и публикует его на своём хостинге: свой сервер не нужен. У каждого приложения есть адрес
`https://<имя>.apps.airlok.ru`, логи, переменные окружения, по желанию база PostgreSQL и загрузка файлов.

У тебя два инструмента:

- **MCP-сервер `airlok`** — всё, кроме загрузки папки: список приложений, выкатка из GitHub, статус и лог сборки, логи
  приложения, переменные, база, домены, настройки. Если инструментов airlok нет, попроси человека один раз выполнить
  `npx @airlok/cli setup` и перезапустить агента.
- **CLI `npx @airlok/cli`** — выкатка папки проекта без GitHub. Всегда с `--json`: итог одной строкой в конце вывода.

## Какое это приложение

1. Если в папке проекта есть `.airlok/project.json`, там `app_id` и `app` — приложение этой папки.
2. Иначе вызови `list_apps` и найди приложение по репозиторию (`repo`) или имени. Не угадывай: если подходит несколько
   или ни одного, спроси человека.
3. Приложения нет — создай его только после согласия человека (см. «Первая выкатка»).

## Выкатка

**Приложение из GitHub** (`repo` не пустой):
- если включена выкатка по push (`auto_deploy`), достаточно закоммитить и запушить в ветку приложения — сборка начнётся
  сама; найди её через `get_app` / `get_deploy_status`;
- иначе `list_commits` (видно, какая версия работает сейчас) и `deploy` с `ref` — веткой или хешем; ответ даёт
  `command_id` для `get_deploy_status`.

**Папка без GitHub** (`repo` пустой или человек просит выкатить «как есть»):

```bash
npx @airlok/cli deploy --json                 # в привязанное приложение
npx @airlok/cli deploy --app <имя> --json      # в существующее
npx @airlok/cli deploy --new <имя> --json      # создать и выкатить
```

CLI сам пропускает `node_modules`, `.git`, `.env*` и сборки, а в git-репозитории — всё из `.gitignore`. Последняя строка
вывода — JSON: `status` (`success`, `failed`, `canceled`), `url`, `message`, `command_id`.

**Первая выкатка**: имя приложения — латиница в нижнем регистре, цифры и дефис, 2–28 символов, с буквы, без `--`. Предложи
имя по папке и спроси человека, прежде чем создавать.

## Сборка: следить и чинить

Сборка идёт от секунд до нескольких минут. `get_deploy_status` с `command_id` показывает этапы (`source` код, `detect`
стек, `install` зависимости, `build` сборка, `image` образ, `release` выкатка) и `log_tail` — конец лога. Опрашивай
раз в 10–20 секунд, пока статус `queued` или `running`.

Если `failed`:
1. Найди этап со статусом `failed` и прочитай `message` и `log_tail` — причина почти всегда в последних строках.
2. Ошибка в коде проекта (сборка, типы, зависимости) — исправь в коде и выкати снова.
3. «Проекту нужны переменные…» — нужны переменные окружения (см. ниже), код не трогай.
4. Не понятно, как запускать (стек определился не тот, нет команды запуска, другой порт) — поправь `airlok.yml` или
   `set_run_settings`.
5. После двух неудачных попыток с одной и той же ошибкой остановись и расскажи человеку, что видишь.

Успешная выкатка с `message` — сборщик что-то поменял сам (например, число рабочих процессов): перескажи человеку.

## Проверить, что работает

1. Открой адрес приложения (`url` из CLI или `domain` из `get_app`): `curl -sS -o /dev/null -w '%{http_code}' <url>`.
   Первый запрос к уснувшему приложению может идти несколько секунд — это нормально.
2. `get_logs` с `errors_only: true` — ошибки приложения после выкатки.
3. `get_app` — `health` (up/down) и причина простоя; `get_metrics` — запросы, 5xx, задержки.
4. Сайт отдаёт 5xx или не отвечает — читай логи, чини, выкатывай снова; сообщи человеку итог с адресом.

## Переменные окружения и секреты

- `list_env` — какие заданы (без значений). `set_env` задаёт, `delete_env` удаляет.
- **Значения секретов (ключи API, пароли, токены) бери только у человека.** Не выдумывай, не подставляй заглушки, не
  выводи значения целиком в ответе.
- `DATABASE_URL`, `PORT`, `UPLOAD_DIR` задаёт сам airlok — их не трогай.
- Переменные, которые встраиваются в код на сборке (`NEXT_PUBLIC_*`, `VITE_*`), действуют только после новой выкатки;
  остальные — сразу, приложение перезапустится само.
- Обязательные переменные проекта перечисли в `airlok.yml` (`env:`) — тогда выкатка без них остановится с понятной
  ошибкой, а не упадёт при запуске.

## airlok.yml — когда определения по файлам не хватает

Файл необязателен: стек (Next.js, Node, Python, статика, Dockerfile, боты) определяется сам. Нужен для базы, загрузок,
задач по расписанию и обязательных переменных. Кладётся в корень проекта.

```yaml
version: 1
app:
  stack: python          # static, nextjs, node, python — если определилось не то
  type: worker           # бот или воркер без сайта; по умолчанию web
build:
  command: npm run build:prod
  output: dist           # каталог готового статического сайта
run:
  command: uvicorn app.main:app --host 0.0.0.0 --port 8080
  release: alembic upgrade head   # один раз перед каждой новой версией
runtime:
  node: "22"             # 20, 22, 24
  python: "3.12"         # 3.10–3.14
capabilities:
  database:
    enabled: true        # PostgreSQL, адрес — в DATABASE_URL
  uploads:
    enabled: true        # файлы пользователей пишутся в UPLOAD_DIR
    max_size_mb: 10
    allowed: [jpg, png, pdf]
  cron:
    - name: отчёт
      schedule: "0 9 * * *"   # время московское
      command: python report.py
      timeout_min: 5
env:
  - OPENAI_API_KEY
```

Веб-приложение слушает `0.0.0.0` и порт из переменной `PORT` (8080). Файловая система, кроме `UPLOAD_DIR`, после
перезапуска очищается: данные храни в базе или загрузках.

## Настройки и остальное

- `get_runtime` / `set_run_settings` — порт, команда запуска, команда перед запуском, нужна ли база (со следующей выкатки).
- `set_always_on` — не засыпать без запросов (боты на вебхуках, WebSocket). Фоновые приложения работают всегда.
- `restart_app` — перезапуск без пересборки, если приложение зависло.
- `get_database` — база и место; `get_uploads` — загруженные файлы и квота; `get_hosting_limits` — лимиты.
- `list_domains`, `add_domain`, `check_domain` — свой домен: после `add_domain` человек добавляет DNS-записи из ответа,
  потом `check_domain`.
- `get_site_settings` / `update_site_settings` — редиректы, заголовки, пароль на сайт, режим обслуживания.
- `list_previews` — превью веток: push в другую ветку собирается на отдельном адресе (включается в дашборде).

## Чего не делать без явной просьбы человека

- создавать приложения, выкатывать в рабочее приложение, менять переменные, домены и настройки сайта;
- удалять переменные (`delete_env`); приложения и домены удаляются только в дашборде;
- печатать токены airlok (`airlok_pat_…`) и значения секретов; коммитить `.env` и `.airlok/`.

Если что-то нельзя сделать инструментами, дай ссылку на дашборд: `dashboard_url` из `get_app` или https://app.airlok.ru.
