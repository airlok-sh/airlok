# Рецепты деплоя

Рецепт настраивает сервер и разворачивает приложение. Приложение получает только те возможности, которые отмечены в манифесте `airlok.yml`, всё остальное закрыто. Пример манифеста и проекта: [examples/nextjs-uploads](../examples/nextjs-uploads).

Проверено на Ubuntu 24.04 и 26.04.

## Стеки и проекты без airlok.yml

Стек определяется по файлам проекта так же, как на хостинге Airlok (`detect.py`):

| Стек | Как узнаётся | Запуск |
| --- | --- | --- |
| Next.js | `next` в package.json | `next start` |
| Node | Express, Nest, Fastify, Koa, Hono, Elysia… или `scripts.start` | `npm run start:prod`, `npm start` или `node server.js`; на Bun без `scripts.start` — `bun run` точки входа |
| Фреймворки с сервером | SvelteKit с `adapter-node`, Nuxt, TanStack Start, React Router, Astro с `@astrojs/node` | собственный сервер фреймворка |
| Python | requirements.txt, pyproject.toml или Pipfile; без них — один `main.py`, `bot.py`, `app.py` и т. п., пакеты выводятся из `import` по известному списку | FastAPI и Starlette — uvicorn, Flask и Django — gunicorn, Streamlit, Gradio |
| Go | `go.mod` в корне; директива `go` — наименьшая версия, собирается на 1.27 | программа из корня или единственного `cmd/*`, собранная `go build` в образе golang |
| Статика | Vite, Astro, CRA, Docusaurus, SvelteKit с `adapter-static`, `nuxt generate`, React Router с `ssr: false`… или `index.html` | nginx в контейнере; без `404.html` любой путь ведёт на `index.html` (SPA); файлам с хешем в имени (`_astro/`, `_next/static/`, `_app/immutable/`, `_nuxt/`, а в `assets/` — JS и CSS) год `immutable`, остальному и HTML — `no-cache` |
| Фоновое | бот (aiogram, telegraf…) без веб-фреймворка или `app.type: worker` | без сайта и порта, работает всегда |

Сборка идёт в той же изолированной песочнице, что и раньше: отдельный пользователь, без секретов и базы, только папка релиза и кэш приложения. Приложение слушает порт из `PORT` на `0.0.0.0`.

Сборка не должна мешать работающим сайтам: все сборки — и обычные, и по Dockerfile — идут в `airlokbuild.slice` с весом CPU 20 против 100 у `system.slice`, где работают сайты, nginx и база (свободный процессор сборка берёт целиком), и с общим мягким пределом памяти; при нехватке памяти сборка гибнет первой. Память одной сборки — три четверти памяти сервера, но не больше свободной за вычетом 256 МБ для сайтов и базы и не меньше 1 ГБ, swap сверху — не больше самой памяти. Slice есть только при драйвере cgroup systemd; без него обычная сборка получает `--cpu-shares 512` (какой это вес в cgroup v2, зависит от версии Docker), а сборка по Dockerfile идёт без пониженного приоритета — как и тогда, когда Docker `--cgroup-parent` не принял.

Между публикациями у каждого приложения свой кэш сборки в `/var/lib/airlok/cache/<имя>`: пакеты npm, pnpm, Yarn, Bun, pip, Go, composer и `.next/cache`. Пределы зависят от диска: кэш одного приложения — десятая часть диска, от 1 до 3 ГБ, сверх него стирается целиком; когда свободно меньше 2 ГБ, сначала стираются кэши других приложений, чьи сборки были давнее всего, и если места всё равно мало, сборка идёт без кэша. Когда меняется любой файл зависимостей (`package.json`, lock-файлы, `requirements.txt`, `pyproject.toml`, `go.mod`, `composer.*` и т. п.), остаются только архивы npm: их npm сверяет с хешами из lock-файла, а остальное могла подменить зависимость, которой в проекте уже нет. Сборка, упавшая с признаками испорченного кэша или нехватки места, один раз повторяется с пустым кэшем. `app-remove.sh` кэш удаляет.

Проверить проект до публикации — `npx @airlok/cli check`: стек, команды, переменные и что помешает публикации, в том числе на своём сервере. Все поля и значения описаны в схеме [`schema/airlok.schema.json`](../schema/airlok.schema.json); строка `# yaml-language-server: $schema=https://raw.githubusercontent.com/airlok-sh/airlok/main/schema/airlok.schema.json` в начале файла включает подсказки и проверку в редакторе.

`airlok.yml` нужен, только если чего-то не хватает: база, загрузки, переменные, свой домен или команды. Без него приложение получает имя из дашборда (при публикации руками — по папке проекта) и адрес `имя.IP-сервера.sslip.io`: он сразу указывает на сервер, и на него можно выпустить сертификат Let's Encrypt. Свой домен можно подключить и кнопкой в дашборде («Домены»): он главнее `app.domain`. Дашборд показывает IP сервера для A-записи и передаёт домен агенту, только когда запись уже указывает на сервер, — иначе публикация увела бы сайт на адрес, который ещё не открывается. Сервер запоминает домен в `/srv/apps/<имя>/shared/panel.domain`, и публикация руками или по webhook на сервере остаётся на нём. В манифесте можно задать то же, что на хостинге:

```yaml
version: 1
app:
  name: shop
  domain: shop.example.ru
  stack: python          # static, nextjs, node, python или go — если определилось не то
  type: web              # worker — бот или воркер без сайта
build:
  command: npm run build:prod
  output: dist           # каталог готового статического сайта
run:
  command: uvicorn shop.api:app --host 0.0.0.0 --port 8080
  health: /healthz       # адрес проверки; без него — главная страница
runtime:
  node: "22"             # 22 или 24 (20 — без исправлений безопасности); без неё — из engines или .nvmrc
  python: "3.12"         # 3.11–3.14 (3.10 — без исправлений безопасности); без неё — из requires-python в pyproject.toml
```

Приложение считается работающим, если главная страница отвечает чем угодно, кроме ошибки 5xx: 401 у закрытого сайта или 404 у API без `/` — тоже ответ. Если задан `run.health`, проверяется он, и нужен успех — 2xx или 3xx. По этому правилу публикация ждёт новую версию (иначе возвращает предыдущую), а проверка сайтов раз в минуту сообщает о простое. Адрес хранится у каждого релиза, поэтому при откате проверяется адрес из его `airlok.yml`.

Переменные окружения проект описывает в `airlok.yml` или в `.env.example` (`.env.sample`, `.env.template`); airlok.yml важнее:

```yaml
env:
  S3_BUCKET: Бакет Object Storage          # строка — описание обязательной переменной
  S3_SECRET_KEY: { secret: true }
  MAX_FILE_SIZE_MB: { default: "10" }      # со значением по умолчанию — необязательная
  SENTRY_DSN: { required: false, description: Ошибки в Sentry }
  SENTRY_AUTH_TOKEN: { secret: true, build: true }   # нужна и сборке
```

Список имён (`env: [OPENAI_API_KEY]`) по-прежнему значит «все обязательные». В `.env.example` пустое значение или заглушка (`your-key`, `changeme`, `<...>`, `PASTE_…_HERE`, `replace_with_…`) — подсказка «проект ждёт переменные»: публикацию она не останавливает, а только перечисляет незаданные; заполненное — необязательная со значением по умолчанию, закомментированная строка — необязательная. Комментарий над строкой становится описанием; если в нём сказано «по умолчанию» или «необязательно», переменная тоже необязательна. `PORT`, `HOST`, `HOSTNAME`, `HOME` и `NODE_ENV` задаёт сам Airlok.

Значения задаются на странице приложения в дашборде или командой `npx @airlok/cli env set ИМЯ --app <имя>`. Браузер и CLI шифруют их под ключ этого сервера (`/etc/airlok/env.key`: его создаёт агент, и сервер он не покидает), поэтому в обычной работе у дашборда есть только шифротекст. Это доверие к сервису, а не гарантия: полную защиту даже от взломанного Airlok даёт строгий режим сервера — тогда значения задаются только на самом сервере. На публикации и при перезапуске из дашборда агент расшифровывает их в `/srv/apps/<имя>/shared/panel.env`, поэтому новые значения доходят до приложения без пересборки — кроме переменных, которые встраиваются в код при сборке. Отпечаток ключа агент пишет в журнал при запуске (`journalctl -u airlok-agent | grep ключ`) — он должен совпадать с тем, что показывает дашборд. Значения можно вписать и прямо на сервере в `/srv/apps/<имя>/shared/user.env` (`ИМЯ=значение`, права 600); заданное в дашборде важнее. Если обязательной переменной из `airlok.yml` или `compose.yml` нет ни там, ни там или она пустая, публикация останавливается до сборки и перечисляет, что задать.

Сборка идёт в песочнице, где работают скрипты чужих пакетов, поэтому значения переменных она получает не все: только `NEXT_PUBLIC_*` и `VITE_*` (фреймворки встраивают их в код) и отмеченные в `airlok.yml` как `build: true`; `build: false` убирает из сборки и переменную с таким префиксом. Скрипты установки зависимостей их тоже видят — секрет отмечайте `build: true`, только если он правда нужен сборке. Готовый релиз того же коммита берётся без пересборки, только если переменные сборки с тех пор не менялись.

В монорепозитории (фронтенд и бэкенд в одном репозитории) приложение не в корне: рецепт назовёт подкаталоги, похожие на проекты, а публиковать каждый нужно отдельным приложением со своим каталогом.

Миграции базы и задачи по расписанию задаются так же, как на хостинге:

```yaml
run:
  release: alembic upgrade head      # перед запуском каждой новой версии
capabilities:
  cron:
    - name: дайджест
      schedule: "0 9 * * 1-5"        # пять полей cron, время московское
      command: python digest.py
      timeout_min: 10                # от 1 до 60, по умолчанию 10
```

Проект с `Dockerfile`, `build.dockerfile` или одним собираемым сервисом в `compose.yml` собирается по нему обычным `docker build`, шаги `RUN` идут в контейнере сборки. Образ запускается так же, как остальные приложения: от отдельного пользователя, с файловой системой только для чтения и без capabilities. Приложение, которое уже собиралось по файлам, собирается по ним дальше, пока не указан `build.dockerfile` или `app.stack: docker`.

Символические ссылки из кода, которые ведут за пределы проекта (абсолютные или через `..` выше его корня), в релиз не попадают: сборка и чтение `airlok.yml` идут от root, и такая ссылка отдала бы им файлы сервера. Ссылки внутри проекта работают. Каталог сборки и Dockerfile из `compose.yml` или `build.dockerfile` проверяются ещё раз уже с развёрнутыми ссылками.

`capabilities.data: { enabled: true }` подключает постоянную папку `/data` (на сервере `/srv/apps/<имя>/shared/data`, путь в `DATA_DIR`) для файлов, которые нельзя перенести в базу, например SQLite. Запускать файлы из неё нельзя. `airlok-backup` кладёт её архив рядом с дампом базы, на время архива приложение замирает.

`run.release` выполняется после бэкапа базы и до запуска новой версии, один раз на сборку: повторная публикация того же собранного релиза её не повторяет. Если команда не прошла или шла дольше 10 минут, новая версия не запускается, а прежняя продолжает работать.

Каждая задача из `capabilities.cron` — таймер systemd `airlok-cron@<имя>_<номер>.timer`. Задача идёт разовым контейнером приложения (`docker compose run`) с той же изоляцией, переменными и базой, на коде текущей версии, а во время публикации ждёт её конца. Если прошлый запуск ещё идёт, следующий пропускается; дольше `timeout_min` задача не работает. Вывод с пометкой `[имя задачи]` и итог запуска уходят в логи приложения в дашборде, полный вывод — в `journalctl -u 'airlok-cron@<имя>_*'`. Запустить задачу сразу, не дожидаясь расписания: `sudo python3 /opt/airlok/recipes/cron.py run <имя>_<номер>` (номер — с нуля, по порядку в `airlok.yml`). Задачи, убранные из `airlok.yml`, выключает следующая публикация. У статического сайта своего кода на сервере нет, поэтому ни `run.release`, ни задач у него быть не может.

## Установка

Одна команда ставит рецепты в `/opt/airlok`, готовит сервер (пакеты, Docker, nginx, ufw, fail2ban) и подключает его к дашборду. Её и токен сервера показывает дашборд; токен установщик спросит сам, не показывая ввод, — так он не остаётся в истории команд. Повторный запуск обновляет рецепты и досоздаёт недостающее.

```bash
sudo bash -c "$(curl -fsSL https://airlok.ru/install.sh)" install https://app.airlok.ru
```

Без терминала (cloud-init, скрипт по SSH) токен передают через stdin: `printf '%s\n' "$AIRLOK_TOKEN" | sudo bash -c …`.

Без дашборда — то же без токена и адреса: `sudo bash -c "$(curl -fsSL https://airlok.ru/install.sh)"`.

Опции после адреса дашборда (их же собирает дашборд, когда вы отмечаете галочки):

| Опция | Что делает |
| --- | --- |
| `--letsencrypt [EMAIL]` | выпускать для сайтов настоящие сертификаты Let's Encrypt вместо самоподписанных; email — для писем о продлении, необязателен |
| `--ssh-keys-only` | последним шагом закрыть вход по паролю. Только если на сервере уже есть ваш SSH-ключ (у root или у того, кто запустил sudo), иначе пароль остаётся |
| `--no-firewall` | не включать ufw |

После `--ssh-keys-only` проверьте вход по ключу в **новом** окне и выполните `confirm-ssh`; если не подтвердить за 3 минуты, вход по паролю вернётся сам. Перезагрузка сервера до подтверждения тоже возвращает пароль: пока закрытие не подтверждено, лежит отметка `/var/lib/airlok/ssh-pending`, и служба `airlok-ssh-guard` при загрузке, до запуска sshd, убирает настройки Airlok. Без опции пароль можно закрыть позже тем же способом:

```bash
sudo /opt/airlok/recipes/server-base.sh ssh
sudo /opt/airlok/recipes/server-base.sh confirm-ssh
```

`AIRLOK_REPO=…` перед командой берёт рецепты из зеркала или локального каталога вместо GitHub.

## Порядок вручную

```bash
cd /opt/airlok/recipes
sudo ./server-base.sh                 # один раз на сервер, вместе с SSH
sudo ./server-base.sh confirm-ssh     # после проверки входа по ключу в новом окне
sudo ./app-deploy.sh /путь/к/проекту  # деплой и каждая следующая публикация
sudo ./app-restart.sh <имя>           # перезапуск той же версии без сборки
sudo ./app-remove.sh <имя>            # убрать с сервера; база, бэкапы и загрузки остаются
sudo ./app-remove.sh <имя> --with-data  # убрать вместе с данными, без возврата
sudo AIRLOK_DB_URL=… AIRLOK_FILES_URL=… ./app-data.sh export|import <имя>  # перенос базы и загрузок при переезде
sudo AIRLOK_DB_URL=… ./app-data.sh backup|restore <имя>  # копия базы в хранилище Airlok и восстановление из неё
sudo ./selftest.sh /путь/к/проекту    # проверка, что песочница работает как обещано
```

Проект Docker Compose приложения называется его именем, а свои контейнеры Airlok узнаёт по папке проекта `/srv/apps/<имя>`. Если на сервере уже есть проект с тем же именем, поднятый из другой папки (например, руками из `~/<имя>`), или чужой том `<имя>_pgdata`, публикация останавливается: назовите приложение иначе. `app-remove.sh` такие контейнеры не трогает, а с `--with-data` удаляет только том базы, который завёл Airlok.

Повторный запуск любого шага безопасен.

## Деплой из GitHub

```bash
sudo ./github-deploy.sh setup  владелец/репозиторий           # ключ и инструкция, куда его добавить
sudo ./github-deploy.sh deploy владелец/репозиторий           # опубликовать main
sudo ./github-deploy.sh deploy владелец/репозиторий a032b88   # опубликовать конкретный коммит или ветку
sudo ./github-deploy.sh log    владелец/репозиторий           # последние коммиты
```

- У каждого репозитория свой deploy key. Добавлять его нужно **без** «Allow write access»: с таким ключом GitHub отклоняет push.
- Ключ хоста github.com зашит в скрипт и сверен с `api.github.com/meta`, поэтому подменить GitHub не получится.
- В релиз попадает только содержимое коммита (`git archive`), без `.git` и истории.
- Релиз называется по хешу коммита. Повторная публикация уже собранного коммита не пересобирает его, поэтому откат занимает секунды: `deploy … <старый-хеш>`.
- Базовые образы (`node`, `python`, `golang`, nginx для статики, `postgres:16` для базы) публикация скачивает заново, но не чаще раза в сутки (после неудачи — раза в час; отметки в `/var/lib/airlok/images`). Node.js, Python, nginx и Postgres обновляются, когда контейнер пересоздаётся, — база при этом перезапускается после копии данных. Go вшит в программу, поэтому у Go-приложения уже собранный коммит после обновления образа `golang` собирается заново. Сборка по Dockerfile идёт с `--pull`; если реестр не отдал базу, она повторяется на образах, что уже есть на сервере.

### Автоматическая публикация по push

```bash
sudo ./github-deploy.sh webhook владелец/репозиторий [ветка]   # по умолчанию main
```

Команда печатает адрес и путь к секрету для GitHub: Settings → Webhooks → Add webhook, Content type `application/json`, событие push. Если приложение уже было развёрнуто раньше, опубликуйте его один раз: так в конфиг nginx добавится адрес webhook.

Как устроено:
- приёмник (`webhook.py`) работает от отдельного пользователя `airlok-hook` в изолированной службе systemd. Он проверяет подпись `X-Hub-Signature-256` до того, как читает содержимое запроса, и только ставит «репозиторий + коммит» в очередь. Ни deploy key, ни прав на деплой у него нет;
- очередь разбирает служба от root (`airlok-deploy-queue`) и ещё раз проверяет оба значения;
- публикуется только push в выбранную ветку. Если во время публикации пришло несколько push, следующей опубликуется последняя версия;
- журнал: `journalctl -u airlok-webhook -u airlok-deploy-queue`.

## Уведомления в Telegram

```bash
sudo ./notify.sh setup   # подключить своего бота, запускать в терминале
sudo ./notify.sh test    # пробное сообщение
```

`setup` попросит создать бота у @BotFather, скрытно спросит токен и сам найдёт ваш чат по сообщению, которое вы отправите боту. Токен хранится только на сервере в `/etc/airlok/telegram.env` с правами 600 и не попадает в аргументы процессов.

Что приходит:
- ✅ версия опубликована: какой коммит и за сколько секунд;
- ⚠️ новая версия не поднялась, вернули предыдущую;
- ❌ публикация не удалась или не началась, с причиной;
- 🔴 сайт не отвечает две проверки подряд, с причиной: контейнер остановлен, не хватило памяти, приложение падает по кругу, nginx не работает, заполнен диск;
- ✅ сайт снова отвечает, с длительностью простоя.

Сайт проверяется каждую минуту (`airlok-healthcheck.timer`). Сообщение приходит только при смене состояния, а не каждую минуту, пока сайт лежит. Во время публикации проверка пропускается. Проверка идёт с самого сервера, поэтому если сервер выключился целиком, сообщить он не сможет.

## Дашборд

```bash
sudo ./notify.sh dashboard https://dash.example.ru   # токен агента спросит, не показывая ввод
```

### Строгий режим

В обычном режиме дашборд не может прислать агенту произвольную команду, но обновление агента и SSH-ключи устройств дают ему полный доступ к серверу, если бэкенд взломан или им распоряжается кто-то недобросовестный. Строгий режим это закрывает: запреты лежат в `/etc/airlok/policy.env`, а этот файл меняет только человек на сервере через `strict.py`.

```bash
git clone https://github.com/airlok-sh/airlok /opt/airlok
git -C /opt/airlok checkout КОММИТ          # прочитайте код этого коммита
sudo /opt/airlok/install.sh https://app.airlok.ru --strict --allow-repo владелец/имя
```

Включить на уже подключённом сервере: `sudo /opt/airlok/recipes/strict.py enable --allow-repo владелец/имя`. Ключи, положенные раньше через дашборд, остаются на сервере: скрипт покажет, откуда их убрать.

Агент отказывает дашборду в обновлении, SSH-ключах, входе по паролю, обновлениях системы, запросах к базе, выгрузке и загрузке данных и удалении вместе с данными. Публиковать можно только коммиты из веток разрешённых репозиториев. Переменные окружения задаются только на сервере, в `/srv/apps/<имя>/shared/user.env`. Логи работы приложений, опись SSH-ключей и входы по SSH в дашборд не уходят; если приложение упало при публикации или перезапуске, его последние строки остаются в `/srv/apps/<имя>/shared/deploy.log`. Замер скорости у посетителей выключен, что бы ни прислал дашборд: он меняет, как nginx отдаёт сайты, а включённый раньше агент снимает.

Новая версия приходит только вручную: `sudo /opt/airlok/recipes/update.sh` покажет, что изменилось, а `update.sh --to КОММИТ` поставит её. Копии базы и постоянной папки остаются на самом сервере, в хранилище Airlok они не уходят. Все команды дашборда, в том числе отклонённые, записаны в `/var/log/airlok-commands.log`.

Что остаётся у дашборда: опубликовать другой коммит или ветку разрешённого репозитория, перезапустить и убрать приложение (данные останутся), сменить его домен. В дашборд по-прежнему уходят память, диск, нагрузка, ОС, доступность сайтов и журнал каждой публикации: сборка не должна печатать секреты. Закрытый репозиторий подключайте доступом только на чтение: с правом записи взломанный бэкенд дописал бы в него ветку и опубликовал её. GitHub App Airlok и так только читает. Агент по-прежнему работает от root: ему нужны Docker и nginx, а доступ к Docker равен root. Защита в том, каким командам он подчиняется.

Токен агента выдаёт дашборд при добавлении сервера. Команда проверяет адрес и токен (`/agent/v1/ping`) и только потом сохраняет их в `/etc/airlok/dashboard.env` с правами 600. После этого в дашборд уходят те же события, что и в Telegram: итог каждой публикации и смена доступности сайта, а при первой проверке — его начальный статус. Раз в минуту сервер сообщает своё состояние: память, диск, нагрузку, открыт ли вход по паролю, включён ли Let's Encrypt.

### Публикация кнопкой из дашборда

Вместе с подключением ставится служба `airlok-agent`. Она сама ходит в дашборд долгим опросом и забирает команды — входящих соединений сервер не принимает. Агент умеет опубликовать указанный коммит репозитория GitHub, перезапустить опубликованное приложение без сборки (`app-restart.sh`), убрать его с сервера (`app-remove.sh`, данные — только если человек отметил это в дашборде), прочитать данные его базы, выгрузить или загрузить базу и загрузки при переезде, сделать ночную копию базы в хранилище Airlok и восстановить её оттуда (`app-data.sh`, по временным ссылкам на хранилище: на время переноса и восстановления приложение останавливается), положить SSH-ключи устройств и обновиться сам, когда это подтвердил человек. Произвольную команду дашборд прислать не может, а каждое поле команды (имя приложения, репозиторий, хеш коммита, ветка, каталог, свой домен) агент проверяет заново.

- Закрытый репозиторий агент забирает по HTTPS с токеном GitHub App, который дашборд выдаёт на одну публикацию: только чтение, только этот репозиторий, живёт час. Токен передаётся git через переменные окружения и не попадает ни в аргументы процессов, ни в логи, ни на диск. Публичный репозиторий забирается без токена.
- В монорепозитории фронтенд и бэкенд — отдельные приложения: у каждого свой каталог проекта и своё имя на сервере, которое задаёт дашборд.
- Долгая команда — публикация, перенос данных, копия или восстановление базы — идёт в фоне, по одной. Пока она идёт, агент берёт быстрые: запрос к базе, ключи устройств, вход по паролю, перезапуск и удаление других приложений (перезапуск и удаление собираемого приложения ждут её конца). Обновление агента и системы ждут, пока агент свободен. Дашборд, который не знает такого опроса, отвечает на него `400`, и тогда агент посреди долгой команды берёт только ключи устройств, а без и этого — работает по одной, как раньше. Вывод быстрых команд посреди долгой — в `/var/lib/airlok/agent/side-command.log`. Публикация и перезапуск приложения идут своими службами systemd (`airlok-publish-ИМЯ`, `airlok-restart-ИМЯ`): остановка агента посылает TERM всем процессам его службы, и `docker compose` посреди смены контейнера оставил бы сайт лежать. Если агент остановили во время сборки, публикация обрывается (контейнер сборки и недособранный релиз удаляются), и в дашборд уходит итог «прервано»; если уже начались копия базы, миграции или смена версии — служба доводит публикацию до конца, а агент после перезапуска дожидается её и отправляет настоящий итог. Так же доводится перезапуск приложения. Быстрая команда, оборванная остановкой, тоже получает итог «прервано» (обновление системы и перезагрузку доводит новый агент). Пока идёт публикация, агент раз в несколько секунд отправляет в дашборд хвост вывода и этапы (код, сборка, запуск, сайт), в конце — итог. Итог сначала ложится в очередь `/run/airlok-results` (tmpfs: в хвосте лога бывает вывод приложения с секретами, а перезапуск службы её не стирает) и сразу отправляется; если дашборд не ответил, агент уже берёт новые команды, а итог доставляет в фоне каждые полминуты. Пока не доставлен итог публикации, берутся только быстрые команды, но не дольше 10 минут. Недоставленный итог живёт час: дальше дашборд уже закрыл команду сам. Паузы после сбоя связи с дашбордом агент растягивает случайной добавкой, чтобы агенты всех серверов не приходили разом после его перезапуска. Последний вывод лежит в `/var/lib/airlok/agent/command.log`.
- Журнал: `journalctl -u airlok-agent`. Обновлённые рецепты агент подхватывает сам между командами.

### Логи приложений в дашборде

Вместе с агентом ставится служба `airlok-logs` (`recipes/logs.py`). Она читает вывод контейнеров приложений через `docker logs` (stdout и stderr по отдельности; у служб кроме `app`, например базы, строка помечена `[db]`) и отправляет его в дашборд: там он хранится неделю, до 20 000 строк на приложение. Собираются только приложения, у которых в дашборде включены логи. У новых приложений они включены сразу, у опубликованных до этой версии их нужно включить в настройках.

- Пока логи приложения открыты в дашборде, строки уходят каждые 200 мс, иначе — раз в 5 секунд. Если логи выключены у всех приложений, служба тихо спрашивает дашборд и смотрит контейнеры раз в полминуты (с небольшим случайным разбросом), а не каждые 5 секунд: включённые логи она подхватит с такой задержкой.
- Больше 200 строк в секунду от одного приложения не отправляется: лишнее отбрасывается, а в логи приходит строка о том, сколько пропущено.
- Пока дашборд недоступен, строки ждут в памяти до 5 МБ, дальше выбрасываются самые старые. Где остановилась в каждом контейнере, служба помнит в `/var/lib/airlok/logs/state.json`, поэтому после перезапуска строки не повторяются.
- Вывод задач по расписанию и команды перед запуском `cron.py` кладёт в очередь `/var/lib/airlok/logs/spool`: разовый контейнер живёт секунды и исчезает раньше, чем служба его заметит.
- Журнал: `journalctl -u airlok-logs`. Полный вывод по-прежнему на сервере: `docker compose -f /srv/apps/<имя>/compose.yml logs app`.

### Обновление агента

Сам агент не обновляется: о новой версии сообщает дашборд, а обновить можно все серверы или выбранные, нажав кнопку. По этой команде агент запускает `update.sh`: забирает ветку `main` в `/opt/airlok`, проверяет подпись новой версии и переходит на неё (`git merge --ff-only`), повторяет базовую настройку сервера, чтобы досоздать то, что появилось в новой версии, обновляет службы, сообщает итог и перезапускается. Единственный параметр команды — хеш коммита (`update.sha`, 40 символов): дашборд может назвать версию, но только из ветки `main` своего репозитория. Кнопка называет версию, которую человек видел в дашборде, а ночное автообновление — последнюю версию, вышедшую не меньше двух суток назад: ошибку в выпуске успевают заметить до того, как она разойдётся по серверам.

Если в `/opt/airlok` есть локальные правки, обновление остановится и покажет причину. То же самое вручную:

```bash
sudo /opt/airlok/recipes/update.sh [--to КОММИТ]
```

#### Подпись версий

Выпуск — это вершина `main`, подписанная SSH-ключом выпускающего: релизный коммит подписывают вручную (`git merge --no-ff -S` или `git commit -S`, `gpg.format=ssh`), подпись всех коммитов подряд не включают. Открытые ключи лежат в [`allowed_signers`](allowed_signers), а на сервере — в `/etc/airlok/allowed_signers`, вне клона: `update.sh` ставит только коммит, подписанный одним из них. Без `--to` он берёт самую новую подписанную вершину `main` после стоящей версии: неподписанные коммиты сверху — ещё не выпуск, и обновление на них не падает. Названный (`--to` или дашбордом) неподписанный коммит не ставится: обновление останавливается с ошибкой «не подписана ключом Airlok», и сервер продолжает работать на прежней версии. Дашборд тоже предлагает только коммит с SSH-подписью, когда в `main` такие есть (чей ключ, проверяет сервер). Подписи GPG и X.509 (в том числе GitHub при слиянии в веб-интерфейсе) не принимаются, поэтому в `main` вливают только локально и с подписью. Проверяется коммит, который ставится, и его подпись ручается за всё дерево: прежде чем подписать коммит поверх чужих, их читают. Перед push вершина `main` должна давать `git log -1 --format=%G? main` = `G`, иначе серверы с ключами её не поставят и останутся на прошлом выпуске.

- Ключи на сервер попадают при установке: `install.sh`, который отдаёт airlok.ru (копия в репозитории лендинга, `deploy/sync-install.py`), несёт их в себе — блок `release_signers` с тем же списком, что `allowed_signers`, это проверяет тест. Первая установка ставит самую новую подписанную вершину `main`, повторный запуск `install.sh` обновляет так же, как `update.sh`. На уже подключённых серверах ключи появляются при первом обновлении новой версией `update.sh` — из уже стоящей версии, до получения новой. Дальше список заменяется списком из каждой новой версии, которую проверили прежние ключи: так ключ меняют без захода на серверы — коммит, добавляющий новый ключ, подписывают старым.
- Пока ключей нет (агент обновился со старой версии или в репозитории ключ ещё не появился), подпись не проверяется — обновление идёт как раньше. Старые агенты подпись не проверяют вовсе и обновляются до первой версии с проверкой как обычно.
- Строгий режим показывает, подписана ли новая версия, рядом с командой `update.sh --to`.
- Потеря ключа без запасного в `allowed_signers` остановит обновления: тогда на каждом сервере заменяют `/etc/airlok/allowed_signers` вручную.

Агент версии раньше 26.10.2026 команду обновления не знает: его один раз обновляют вручную командой, которую покажет дашборд.

## Обновления системы

Автообновления безопасности включает `server-base.sh`. Остальное агент ставит только по подтверждению человека: в каждой отметке он присылает, сколько обновлений не поставлено, сколько из них исправлений безопасности и нужна ли перезагрузка (`osupdates.py`; подсчёт повторяется, только когда сменились списки или установленные пакеты), а кнопка в дашборде или `npx @airlok/cli server upgrade <имя>` запускает `os-upgrade.sh`.

- Считается и ставится один и тот же набор — как у `apt upgrade`: новые зависимости ставятся, ничего не удаляется, изменённые руками настройки остаются, отложенные фазами обновления не считаются.
- Перед установкой проверяются память со swap (от 300 МБ) и диск (от 1 ГБ, `/boot` от 150 МБ). Занятый apt ждём до 10 минут.
- Установка идёт отдельной службой `airlok-os-upgrade`: перезапуск агента её не оборвёт, а новый агент дождётся конца и отправит итог. Приложения не перезапускаются: у Docker включён `live-restore`. После установки агент сверяет, что работают все контейнеры, что работали до неё. Пока она идёт, проверка сайтов пропускается.
- Перезагрузка — только отдельным подтверждением. Итог отправляется после неё: успех значит, что сервер вернулся и приложения снова работают.

### База в дашборде

Вкладка «База» и инструмент MCP `query_database` читают Postgres приложения через агента (`recipes/dbquery.py`). Агент подключается к контейнеру базы от роли `airlok_ro`: она может только читать (`pg_read_all_data`) и не суперпользователь, поэтому ни изменить данные, ни выполнить команду в системе через неё нельзя. Каждый запрос — один оператор в транзакции только на чтение, до 5 секунд, и строк база отдаёт не больше, чем просили. Роль заводится при первом запросе, её пароль — в `/srv/apps/<имя>/shared/db-ro.env`. Агент выполняет команды по очереди, поэтому пока идёт публикация, запрос ждёт её конца.

### Доступ устройств по SSH

В разделе «Устройства» дашборда человек хранит открытые SSH-ключи своих компьютеров и отмечает, каким серверам какое устройство открыто. Агент получает полный список ключей этого сервера и записывает их в `authorized_keys` пользователя сервера (`recipes/sshkeys.py`; путь — из `AuthorizedKeysFile` в настройках sshd) строками с пометкой `airlok-device:<id>`. Пользователь по умолчанию — root; если хостер не пускает root по SSH, в окне «SSH» у сервера выбирают другого (из тех, кого назвал агент: uid от 1000, оболочка для входа, домашний каталог). У остальных пользователей агент строки устройств убирает. В чужой домашний каталог он пишет от root, поэтому ссылки (`~/.ssh` на другой каталог) не проходит.

- Строки без пометки — ключи хостера и добавленные руками — агент не трогает. Исключение — тот же ключ, что у устройства: его строка заменяется помеченной, иначе отключение устройства в дашборде не закрыло бы ему доступ. Опции строки (`command=`, `from=`, `restrict`) помеченная строка сохраняет — если в файле нет копии ключа без опций; в опись уходит только признак `restricted` (опции на всех строках ключа в файле), сами опции — нет. При смене пользователя ключ устройства переезжает с опциями только из файлов root и учёток с тем же uid, что у выбранного пользователя: чужой `command=` выполнился бы от его имени. Ключ, который у других пользователей лежит только с опциями, выбранному пользователю агент не кладёт и строку оставляет на месте — без опций он стал бы полным входом; об этом агент пишет в итоге команды. В счёт идут и строки без пометки: ключ могли сделать устройством и сменить пользователя раньше, чем агент пометил строку.
- Последний ключ root агент не уберёт, если войти root'ом по паролю нельзя: сервер остался бы без входа.
- Файл переписывается целиком через временный рядом и только когда в нём что-то меняется; права 600.
- В каждой отметке (`healthcheck.sh`) агент присылает опись `authorized_keys` этих пользователей — когда она изменилась и раз в час — и входы по SSH из журнала sshd (`sshkeys.py report`): дашборд показывает ключи, положенные мимо Airlok, и последние входы, предупреждает о новом таком ключе и о входе по паролю. Где агент остановился в журнале, лежит в `/var/lib/airlok/health/ssh-logins.cursor`; прошлые входы при первом запуске не досылаются.

Кнопкой «Закрыть» у сервера дашборд закрывает вход по паролю — когда серверу открыто устройство и его ключ уже на месте. Агент запускает `server-base.sh ssh` с откатом и ждёт до 5 минут, пока на сервер войдут новым соединением по ключу устройства (`sshkeys.py wait-login` читает журнал sshd). Увидел — закрепляет настройку, не дождался — сразу возвращает вход по паролю. Вход другим ключом не в счёт: на сервер ходят и скрипты, а проверить нужно ключ человека. Ключ устройства с опциями (`command=`, `from=`) тоже не в счёт. «Открыть» убирает настройки Airlok (`server-base.sh ssh-open`); если вход по паролю выключил хостер, он так и останется выключенным.

### Метрики

nginx пишет для каждого сайта отдельный лог `/var/log/nginx/airlok-<имя>.access.log` в коротком формате: время, код ответа, длительность, размер, метод, путь и время ответа приложения. IP посетителей и query-строка не пишутся, путь уходит в дашборд только шаблоном (`/orders/:id`). Раз в минуту `metrics.py` считает по законченным минутам число запросов, ошибки 4xx и 5xx, объём и время ответа приложения (медиана и 95-й перцентиль) и отправляет в дашборд. Время ответа берётся из `$upstream_response_time`, а не из длительности запроса: в неё входят приём тела запроса и отдача ответа, и медленный клиент дал бы секунды там, где приложение ответило за миллисекунду. Если ответил сам nginx (например, 413 на слишком большое тело), берётся длительность. Если дашборд недоступен, минуты копятся в `/var/lib/airlok/metrics` до 7 дней.

Скорость у посетителей (Web Vitals) — как на хостинге. В ответ на отправку метрик дашборд называет приложения, у которых замер включён на вкладке «Скорость», поэтому `metrics.py` отправляет их каждую минуту, даже пустыми. Для таких приложений `speed.py` кладёт сниппет `/etc/nginx/snippets/airlok-speed.<имя>.conf`: nginx просит у приложения страницы несжатыми, дописывает перед `</head>` скрипт `speed.js` (копия `internal/edge/speed.js` из backend, лежит в `/usr/share/airlok`), сам его отдаёт и отвечает 204 на маячки `/_airlok/v`, не трогая приложение. Маячки пишутся в `/var/log/nginx/airlok-<имя>.speed.log` без IP — время, путь страницы, показатели и браузер; с одного адреса не больше 5 в секунду. `metrics.py` складывает их в гистограммы, как edge, отправляет вместе с минутой и стирает прочитанное; в дашборд браузер не уходит, только «телефон» или «компьютер». Строку `include` сниппета шаблон сайта в `app-deploy.sh` содержит сам, а в сайты, опубликованные раньше, её дописывает `speed.py`. Если `nginx -t` не принял конфиг, файлы возвращаются как были. Выключение убирает сниппет.

События сначала записываются в очередь `/var/lib/airlok/events` (права 700) и уже потом отправляются, поэтому недоступность дашборда их не теряет:
- очередь отправляется по порядку сразу после нового события и ещё раз каждую минуту вместе с проверкой сайтов;
- если нет связи, дашборд отвечает ошибкой, просит подождать или не принимает токен, событие остаётся в очереди до следующей попытки;
- если дашборд отверг само событие (400 или 413), оно перекладывается в `failed/`, чтобы не задерживать остальные;
- у каждого события есть `id` и время. Повтор не задваивает историю, в ней показывается время события, а не время доставки, а более старое событие не перетирает более новый статус сайта;
- в очереди хранится до 1000 событий, в `failed/` — до 100, самые старые удаляются.

Публикация и проверки от доступности дашборда не зависят.

Пока сертификат самоподписанный, в настройках webhook GitHub приходится отключать проверку SSL. Подпись запроса это не ослабляет, но для настоящего домена выпустите сертификат и включите проверку обратно.

## Let's Encrypt

```bash
sudo ./server-base.sh letsencrypt [email]   # или опция --letsencrypt установщика
```

Ставит certbot и включает выпуск: сертификат для домена приложения выпускается при публикации через webroot (`/.well-known/acme-challenge/` на 80-м порту) и продлевается сам (`certbot.timer`, после продления nginx перечитывает конфиг). A-запись домена должна указывать на сервер. Если выпустить не вышло, публикация не падает: сайт работает с самоподписанным сертификатом, а следующая публикация попробует снова. Причина — в `/srv/apps/<имя>/shared/letsencrypt.log`.

## Что делает каждый шаг

**server-base.sh**

Его запускают установка и каждое обновление агента, поэтому то, что человек настроил на сервере сам, он дополняет, а не переписывает. Повторный запуск он узнаёт по уже настроенному nginx или подключению к дашборду.
- если apt занят, например автообновлениями на только что арендованном сервере, ждёт до 10 минут и только потом сообщает об этом;
- списки пакетов моложе 10 минут (отметка `/var/lib/airlok/apt-lists.stamp` или ежедневное обновление самой Ubuntu) заново не скачивает, а когда все нужные пакеты уже стоят, apt не трогает вовсе: обновление агента не качает списки каждый раз, а новые версии этих пакетов приносят автообновления безопасности;
- при повторном запуске проверяет только версию Ubuntu: нехватка места — лишь предупреждение, а занятые не nginx порты 80 и 443 не мешают обновлению;
- автообновления безопасности, swap;
- Docker из Ubuntu (`docker.io`), только если на сервере ещё нет Docker. Docker CE с download.docker.com остаётся, к нему при необходимости ставятся `docker-compose-plugin` и `docker-buildx-plugin`. Docker из snap или без `docker compose` — установка останавливается с объяснением;
- в `/etc/docker/daemon.json` дописываются ротация логов и `live-restore`, если они не заданы ни в файле, ни флагами dockerd; `data-root`, зеркала и прочие ключи остаются, файл не в формате JSON не трогается. `no-new-privileges` для всех контейнеров включается только на чистом сервере, где ещё нет контейнеров, — контейнеры Airlok запускаются с ним и так. Docker перезапускается, только если файл изменился, а если при этом работают контейнеры, сначала включается `live-restore`, чтобы они не остановились. Не запустился — файл возвращается как был;
- проверяет, отвечает ли с сервера Docker Hub (с него публикации берут образы сборки, nginx и Postgres). Если нет и зеркало в `registry-mirrors` не задано — предупреждает и подсказывает, как его настроить; установку это не останавливает. Проверяется только реестр (`registry-1.docker.io/v2/`): слои образов Hub отдаёт с Cloudflare R2, и если медленно именно они, это покажет первая публикация. Сам Airlok зеркало не добавляет;
- ufw включается только при первой установке (если нет `--no-firewall`): открыты SSH (все порты из `sshd -T` и `ssh.socket`), 80, 443 и все порты, которые уже слушают не только на localhost, — VPN и свои сервисы продолжают работать. При обновлении во включённый ufw только добавляются SSH, 80 и 443, а выключенный больше не включается. Что вышло, записано в `FIREWALL` в `/etc/airlok/server.env`: `airlok` — включён, `off` — выключен;
- сайт nginx по умолчанию убирается, только если он такой, каким его поставил пакет, и в `/var/www/html` нет своих файлов. Иначе он остаётся, и запросы по IP сервера идут в него;
- fail2ban, nginx без версии в заголовках;
- в сайты, опубликованные раньше, дописывается запрет отдавать из загрузок ссылки на чужие файлы (как в шаблоне `app-deploy.sh`). Конфиг, правленный руками, не трогается; если `nginx -t` не принял правку, файлы возвращаются как были;
- вход по SSH только по ключу. Если не выполнить `confirm-ssh` за 3 минуты или перезагрузить сервер до подтверждения, настройка SSH откатится сама, так что доступ к серверу не потеряется.

**app-deploy.sh**
- не публикует, если домен из манифеста уже занят другим сайтом на сервере: иначе nginx молча отдавал бы его старому сайту;
- отдельный пользователь Linux для приложения, без входа и sudo;
- код принадлежит root и смонтирован в контейнер только на чтение;
- сборка в отдельном контейнере без секретов и доступа к базе;
- если сборка, база или приложение не запустились, потому что Docker Hub с сервера недоступен или упёрся в лимит запросов, к ошибке дописывается «Причина — Docker Hub» и как настроить зеркало. Сюда входят и сбои скачивания слоёв с Cloudflare R2, о которых dockerd пишет без имени Hub. «Образ не найден», «нет доступа» и неверный `docker login` сюда не относятся;
- новый `static.conf` перед заменой проверяет настоящий nginx из образа статики, а новый конфиг сайта на хосте — `nginx -t`: непринятый конфиг не ставится, публикация останавливается, сайт остаётся на прежнем, остальные не затронуты;
- nginx сайта сжимает gzip текст, JS, CSS, JSON, XML и SVG от 1 КБ, если приложение не сжало ответ само; поток событий (`text/event-stream`) не сжимается;
- контейнер приложения: файловая система только на чтение, без привилегий, порт только на `127.0.0.1`, лимиты памяти и процессов;
- загрузки — единственная папка с записью, смонтирована с `noexec`;
- nginx отдаёт из загрузок только разрешённые расширения, с `nosniff` и CSP sandbox, не картинки — только на скачивание. Ссылку, которую приложение положило в загрузки, nginx отдаёт, только если она ведёт на файл самого приложения: загрузки соседних приложений, журналы nginx и код релизов так не скачать;
- закрытые загрузки (`uploads.public: false`) принадлежат группе приложения, а не nginx: nginx их не прочтёт, и ссылкой из соседнего приложения их не достать. У опубликованного раньше приложения группа меняется при следующей публикации, после нового конфига сайта;
- Postgres без опубликованных портов, ежедневный дамп и дамп перед каждой публикацией;
- команда перед запуском и задачи по расписанию — в разовых контейнерах приложения с теми же ограничениями;
- если новая версия не ответила за 2 минуты, возвращается предыдущая.

**selftest.sh** проверяет всё перечисленное изнутри контейнера, на сервере и через nginx.

## Где что лежит

| Путь | Что |
| --- | --- |
| `/srv/apps/<имя>/releases/` | релизы, `current` — активный |
| `/srv/apps/<имя>/shared/uploads/` | загрузки пользователей |
| `/srv/apps/<имя>/shared/user.env` | ваши секреты (`OPENAI_API_KEY=…`), права 600 |
| `/srv/apps/<имя>/shared/panel.domain` | свой домен из дашборда, который прислал агент; по нему идут и публикации без агента |
| `/srv/apps/<имя>/shared/panel.env` | переменные из дашборда, расшифрованные агентом; заменяется на каждой публикации и перезапуске из дашборда |
| `/etc/airlok/env.key` | закрытый ключ, под который дашборд шифрует переменные; сервер не покидает |
| `/srv/apps/<имя>/shared/backups/` | дампы базы, 7 последних |
| `/var/lib/airlok/cache/<имя>` | кэш сборки приложения (рядом — `<имя>.deps` с отпечатком зависимостей и `<имя>.used` со временем последней сборки) |
| `/srv/apps/<имя>/shared/cron.json` | задачи по расписанию опубликованной версии; таймеры — `/etc/systemd/system/airlok-cron@<имя>_*.timer` |
| `/srv/apps/<имя>/shared/released` | релиз, для которого `run.release` уже выполнена |
| `/srv/apps/<имя>/shared/db-ro.env` | пароль роли `airlok_ro`, от которой дашборд читает базу; права 600 |
| `/etc/nginx/sites-available/airlok-<имя>.conf` | конфиг сайта |
| `/var/log/nginx/airlok-<имя>.access.log` | лог запросов для метрик |
| `/etc/airlok/server.env` | настройки сервера: Let's Encrypt, включён ли ufw (`FIREWALL`) |
| `/etc/airlok/dashboard.env` | адрес дашборда и токен агента, права 600 |

## Чего пока нет

- `outbound_network: false` описан в формате манифеста, но рецепт его пока не поддерживает и честно останавливается.
- Без `--letsencrypt` сертификат самоподписанный.
- Бэкапы лежат на том же сервере.
- Внешней проверки доступности (с другого сервера) пока нет.
- Подмодули git не поддерживаются.
