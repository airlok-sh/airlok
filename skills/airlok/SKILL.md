# airlok

airlok собирает проект и публикует его. Приложение живёт в одном из двух мест — это поле `hosted` в `list_apps`:

- **хостинг airlok** (`hosted: true`) — свой сервер не нужен; адрес `https://<имя>.apps.airlok.ru`, логи, переменные,
  по желанию база PostgreSQL и загрузка файлов, свои домены;
- **свой сервер пользователя** (`hosted: false`, поле `server`) — VPS, на котором стоит агент airlok; выкатка только из
  GitHub, адрес — из `app.domain` в `airlok.yml` или `имя.IP-сервера.sslip.io`; логи агент отправляет в airlok, если
  у приложения они включены.

У тебя два инструмента:

- **MCP-сервер `airlok`** — список приложений и серверов, выкатка из GitHub, статус и лог сборки, переменные, логи, а
  для хостинга ещё база, домены и настройки. Если инструментов airlok нет, попроси человека один раз выполнить
  `npx @airlok/cli setup` и перезапустить агента.
- **CLI `npx @airlok/cli`** — проверка проекта (`check`), выкатка папки на хостинг без GitHub (`deploy`), переменные
  своего сервера (`env`), подключение своего сервера (`server connect`). Для скриптов и тебя — с `--json`: итог одной строкой.

## Проверить проект до выкатки

```bash
npx @airlok/cli check --json
```

`check` показывает, что airlok сделает с папкой, ничего не собирая: стек, команды установки, сборки и запуска, адрес
проверки, базу, загрузки, все переменные (обязательные, секреты, переменные сборки) и что помешает выкатке. Запускай его
перед первой выкаткой и после каждой правки `airlok.yml`. В JSON: `status` (`ok` или `error`), `errors` — остановят
выкатку, `warnings` — скорее всего ошибка (например, опечатка в поле `airlok.yml`), `notes` — подсказки, `server` — чего
нет на своём сервере. Код выхода 1 — с такими файлами выкатка не пройдёт: сначала исправь `errors`.

## Какое это приложение

1. Если в папке проекта есть `.airlok/project.json`, там `app_id` и `app` — приложение этой папки.
2. Иначе вызови `list_apps` и найди приложение по репозиторию (`repo`) или имени. Не угадывай: если подходит несколько
   или ни одного, спроси человека.
3. Приложения нет — создай его только после согласия человека (см. «Первая выкатка»).

## Выкатка

**Приложение из GitHub** (`repo` не пустой):
- если включена выкатка по push (`auto_deploy`), достаточно закоммитить и запушить в ветку приложения — сборка начнётся
  сама; найди её через `get_app` / `get_deploy_status`;
- иначе `list_commits` (видно, какая версия работает сейчас) и `deploy` с `ref` — веткой или хешем; ответ даёт
  `command_id` для `get_deploy_status`.

На своём сервере выкатка идёт так же через `deploy`; этапы в `get_deploy_status` там другие: `source` код, `build`
зависимости и сборка, `start` запуск и ожидание ответа, `site` nginx и HTTPS. Если новая версия не ответила, агент
возвращает прежнюю: выкатка `failed` с сообщением «вернули предыдущую», а в `get_app` — выкатка `rolled_back`.

**Папка без GitHub, только хостинг** (`repo` пустой или человек просит выкатить «как есть»):

```bash
npx @airlok/cli deploy --json                 # в привязанное приложение
npx @airlok/cli deploy --app <имя> --json      # в существующее
npx @airlok/cli deploy --new <имя> --json      # создать и выкатить
```

CLI сам пропускает `node_modules`, `.git`, `.env*` и сборки, а в git-репозитории — всё из `.gitignore`. Последняя строка
вывода — JSON: `status` (`success`, `failed`, `canceled`), `url`, `message`, `command_id`.

**Первая выкатка**: имя приложения — латиница в нижнем регистре, цифры и дефис, 2–28 символов, с буквы, без `--`. Предложи
имя по папке и спроси человека, прежде чем создавать.

## Сборка: следить и чинить

Сборка идёт от секунд до нескольких минут. `get_deploy_status` с `command_id` показывает этапы (`source` код, `detect`
стек, `install` зависимости, `build` сборка, `image` образ, `release` выкатка) и `log_tail` — конец лога. Опрашивай
раз в 10–20 секунд, пока статус `queued` или `running`.

Если `failed`:
1. Найди этап со статусом `failed` и прочитай `message` и `log_tail` — причина почти всегда в последних строках.
2. Ошибка в коде проекта (сборка, типы, зависимости) — исправь в коде и выкати снова.
3. «Проекту нужны переменные…» или «не заданы обязательные переменные» — нужны переменные окружения (см. ниже), код
   не трогай.
4. Не понятно, как запускать (стек определился не тот, нет команды запуска, другой порт) — поправь `airlok.yml` или
   `set_run_settings`.
5. «проверка /… из airlok.yml (run.health) ответила 404» — адреса проверки нет в приложении: поправь `run.health` или
   код. «приложение не ответило за 2 минуты» — оно не слушает `0.0.0.0` и порт из `PORT`.
6. «переменные окружения из дашборда: … не расшифровать» — на своём сервере сменился ключ: человек задаёт значения
   заново (см. «Переменные»).
7. После двух неудачных попыток с одной и той же ошибкой остановись и расскажи человеку, что видишь.

Успешная выкатка с `message` — сборщик что-то поменял сам (например, число рабочих процессов): перескажи человеку.

## Проверить, что работает

1. Открой адрес приложения (`url` из CLI или `domain` из `get_app`): `curl -sS -o /dev/null -w '%{http_code}' <url>`.
   Первый запрос к уснувшему приложению может идти несколько секунд — это нормально.
2. `get_logs` с `errors_only: true` — ошибки приложения после выкатки. Если `get_logs` пишет, что сбор логов выключен
   или агент старый, попроси человека включить логи в настройках приложения или обновить агент; до тех пор логи
   своего сервера читает человек: `docker compose -f /srv/apps/<имя>/compose.yml logs --tail 100 app`.
3. `get_app` — `health` (up/down) и причина простоя; `get_metrics` — запросы, 5xx, задержки. Приложение считается
   живым, если главная отвечает чем угодно, кроме 5xx, а с `run.health` — если этот адрес отвечает 2xx или 3xx.
4. Сайт отдаёт 5xx или не отвечает — читай логи, чини, выкатывай снова; сообщи человеку итог с адресом.

## Переменные окружения и секреты

- `list_env` — какие заданы (без значений). `set_env` задаёт, `delete_env` удаляет.
- **Значения секретов (ключи API, пароли, токены) бери только у человека.** Не выдумывай, не подставляй заглушки, не
  выводи значения целиком в ответе.
- **Приложение на своём сервере**: значения шифруются под ключ сервера, и airlok их не видит — `set_env` для него
  откажет. Попроси человека задать их на странице приложения в дашборде или выполнить у себя
  `npx @airlok/cli env set ИМЯ --app <имя>` (значение спросит без показа) или `npx @airlok/cli env set --app <имя> --from .env`.
  Попадут на сервер при следующей выкатке. `list_env` покажет заданные; `stale: true` — значение под прежним ключом
  сервера, его нужно задать заново. Если агент сервера старый и ключа нет, значения вписывают на сервере в
  `/srv/apps/<имя>/shared/user.env` или обновляют агента в дашборде (Серверы → «Обновить»).
- `DATABASE_URL`, `PORT`, `UPLOAD_DIR` задаёт сам airlok — их не трогай.
- Переменные, которые встраиваются в код на сборке (`NEXT_PUBLIC_*`, `VITE_*`), действуют только после новой выкатки;
  остальные на хостинге — сразу, приложение перезапустится само. На своём сервере все переменные применяются новой
  выкаткой, а в сборку попадают только `NEXT_PUBLIC_*`, `VITE_*` и отмеченные `build: true`.
- Переменные проекта опиши в `airlok.yml` (`env:`) или в `.env.example`: пустое значение там — обязательная
  переменная, заполненное — необязательная со значением по умолчанию, комментарий над строкой — описание. Дашборд
  покажет их до выкатки, а без обязательных выкатка остановится с понятной ошибкой, а не упадёт при запуске. Как
  собрать полный список с описаниями — навык `airlok-yml`.

## airlok.yml — когда определения по файлам не хватает

Файл необязателен: стек (Next.js, Node, Python, Go, статика, Dockerfile, боты) определяется сам. Нужен для базы, загрузок,
задач по расписанию и переменных. Кладётся в корень проекта (в монорепозитории — в папку приложения). Первая строка —
схема: редактор и ты сразу увидите опечатки и неверные значения. Как собрать файл целиком — навык `airlok-yml`; после
правки — `npx @airlok/cli check`.

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/airlok-sh/airlok/main/schema/airlok.schema.json
version: 1
app:
  stack: python          # static, nextjs, node, python, go, docker — если определилось не то
  type: worker           # бот или воркер без сайта; по умолчанию web
build:
  command: npm run build:prod
  output: dist           # каталог готового статического сайта
run:
  command: uvicorn app.main:app --host 0.0.0.0 --port 8080
  release: alembic upgrade head   # один раз перед каждой новой версией
  health: /healthz       # адрес проверки: должен отвечать 2xx; без него годится любой ответ главной, кроме 5xx
runtime:
  node: "22"             # 20, 22, 24
  python: "3.12"         # 3.10–3.14
  go: "1.27"             # 1.25–1.27, по умолчанию из директивы go в go.mod
capabilities:
  database:
    enabled: true        # PostgreSQL, адрес — в DATABASE_URL
  uploads:
    enabled: true        # файлы пользователей пишутся в UPLOAD_DIR
    max_size_mb: 10
    allowed: [jpg, png, pdf]
  cron:
    - name: отчёт
      schedule: "0 9 * * *"   # время московское
      command: python report.py
      timeout_min: 5
env:
  OPENAI_API_KEY: Ключ API OpenAI         # строка — описание обязательной переменной
  SESSION_SECRET: { secret: true }        # дашборд предложит сгенерировать
  MAX_TOKENS: { default: "1000" }         # со значением по умолчанию — необязательная
  SENTRY_AUTH_TOKEN: { secret: true, build: true, required: false }   # нужна и сборке
```

Только на хостинге: `app.stack: docker`, `build.dockerfile` и `capabilities.cron`. Свой сервер Dockerfile не читает и
собирает проект по его файлам (`go.mod`, `package.json`…) — это не ошибка; не пройдёт только явный `app.stack: docker`. Только на своём сервере: `app.domain`
(домен сайта) и `resources.memory_mb` (память контейнера, 128–8192, по умолчанию 512).

Веб-приложение слушает `0.0.0.0` и порт из переменной `PORT` (8080). Файловая система, кроме `UPLOAD_DIR`, после
перезапуска очищается: данные храни в базе или загрузках.

## Подключить свой сервер

Человек просит подключить VPS к airlok — выполни в терминале:

```bash
npx @airlok/cli server connect root@IP-СЕРВЕРА --json [--letsencrypt] [--email почта] [--ssh-keys-only] [--name имя]
```

CLI сам заведёт сервер в дашборде, поставит на него airlok по SSH (Docker, nginx, файрвол, агент — несколько минут) и
дождётся, когда агент выйдет на связь. Токен агента CLI передаёт на сервер сам: ни тебе, ни в вывод он не попадает.

- Флаги бери из просьбы человека или из промпта, который он скопировал из дашборда; сам `--ssh-keys-only` не добавляй:
  он закрывает вход на сервер по паролю.
- «пароль здесь ввести негде» — сервер ещё не пускает по ключу, а ssh спрашивает пароль только в настоящем терминале.
  Попроси человека выполнить ту же команду в своём терминале (Терминал на macOS, PowerShell на Windows) и ввести пароль
  от сервера там. **Пароль от сервера у человека не спрашивай и в команды не подставляй.** После этого повторный запуск
  у тебя пройдёт по ключу `~/.ssh/airlok_ed25519`.
- «Установка не закончилась» — причина в выводе установщика выше; исправь, если можешь (например, не Ubuntu 24.04/26.04
  или меньше 1 ГБ памяти — тогда скажи человеку), и запусти команду снова: она продолжит с того же места.
- «ключ сервера не совпадает» — не выполняй `ssh-keygen -R` сам: спроси человека, переустанавливал ли он сервер.
- Итог `status: "ok"` — сервер на связи, в `ssh` команда входа. Дальше выкатка на него — из GitHub, как обычно.

## Настройки и остальное

- `list_servers` — свои серверы: на связи ли агент, его версия, ОС, закрыт ли вход по паролю. Агента обновляет человек в
  дашборде (Серверы → «Обновить»); без новой версии нет, например, переменных из дашборда.

Дальше — только для хостинга:

- `get_runtime` / `set_run_settings` — порт, команда запуска, команда перед запуском, нужна ли база (со следующей выкатки).
- `set_always_on` — не засыпать без запросов (боты на вебхуках, WebSocket). Фоновые приложения работают всегда.
- `restart_app` — перезапуск без пересборки, если приложение зависло.
- `get_database` — база и место; `get_uploads` — загруженные файлы и квота; `get_hosting_limits` — лимиты.
- `list_domains`, `add_domain`, `check_domain` — свой домен: после `add_domain` человек добавляет DNS-записи из ответа,
  потом `check_domain`.
- `get_site_settings` / `update_site_settings` — редиректы, заголовки, пароль на сайт, режим обслуживания.
- `list_previews` — превью веток: push в другую ветку собирается на отдельном адресе (включается в дашборде).

## Чего не делать без явной просьбы человека

- создавать приложения, выкатывать в рабочее приложение, менять переменные, домены и настройки сайта;
- удалять переменные (`delete_env`); приложения и домены удаляются только в дашборде;
- печатать токены airlok (`airlok_pat_…`) и значения секретов; коммитить `.env` и `.airlok/`.

Если что-то нельзя сделать инструментами, дай ссылку на дашборд: `dashboard_url` из `get_app` или https://app.airlok.ru.
