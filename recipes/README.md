# Рецепты деплоя

Рецепт настраивает сервер и разворачивает приложение. Приложение получает только те возможности, которые отмечены в манифесте `airlok.yml`, всё остальное закрыто. Пример манифеста и проекта: [examples/nextjs-uploads](../examples/nextjs-uploads).

Проверено на Ubuntu 24.04 и 26.04.

## Стеки и проекты без airlok.yml

Стек определяется по файлам проекта так же, как на хостинге airlok (`detect.py`):

| Стек | Как узнаётся | Запуск |
| --- | --- | --- |
| Next.js | `next` в package.json | `next start` |
| Node | Express, Nest, Fastify, Koa, Hono… или `scripts.start` | `npm run start:prod`, `npm start` или `node server.js` |
| Python | requirements.txt, pyproject.toml или Pipfile | FastAPI и Starlette — uvicorn, Flask и Django — gunicorn, Streamlit, Gradio |
| Go | `go.mod` в корне, версия — из директивы `go` (1.25–1.27) | программа из корня или единственного `cmd/*`, собранная `go build` в образе golang |
| Статика | Vite, Astro, CRA, Docusaurus… или `index.html` | nginx в контейнере; без `404.html` любой путь ведёт на `index.html` (SPA) |
| Фоновое | бот (aiogram, telegraf…) без веб-фреймворка или `app.type: worker` | без сайта и порта, работает всегда |

Сборка идёт в той же изолированной песочнице, что и раньше: отдельный пользователь, без секретов и базы, только папка релиза. Приложение слушает порт из `PORT` на `0.0.0.0`.

Проверить проект до выкатки — `npx @airlok/cli check`: стек, команды, переменные и что помешает выкатке, в том числе на своём сервере. Все поля и значения описаны в схеме [`schema/airlok.schema.json`](../schema/airlok.schema.json); строка `# yaml-language-server: $schema=https://raw.githubusercontent.com/airlok-sh/airlok/main/schema/airlok.schema.json` в начале файла включает подсказки и проверку в редакторе.

`airlok.yml` нужен, только если чего-то не хватает: база, загрузки, переменные, свой домен или команды. Без него приложение получает имя из дашборда (при выкатке руками — по папке проекта) и адрес `имя.IP-сервера.sslip.io`: он сразу указывает на сервер, и на него можно выпустить сертификат Let's Encrypt. Свой домен можно подключить и кнопкой в дашборде («Домены»): он главнее `app.domain`. Дашборд показывает IP сервера для A-записи и передаёт домен агенту, только когда запись уже указывает на сервер, — иначе выкатка увела бы сайт на адрес, который ещё не открывается. Сервер запоминает домен в `/srv/apps/<имя>/shared/panel.domain`, и выкатка руками или по webhook на сервере остаётся на нём. В манифесте можно задать то же, что на хостинге:

```yaml
version: 1
app:
  name: shop
  domain: shop.example.ru
  stack: python          # static, nextjs, node, python или go — если определилось не то
  type: web              # worker — бот или воркер без сайта
build:
  command: npm run build:prod
  output: dist           # каталог готового статического сайта
run:
  command: uvicorn shop.api:app --host 0.0.0.0 --port 8080
  health: /healthz       # адрес проверки; без него — главная страница
runtime:
  node: "22"             # 20, 22 или 24
  python: "3.12"         # 3.10–3.14; без неё — из requires-python в pyproject.toml
```

Приложение считается работающим, если главная страница отвечает чем угодно, кроме ошибки 5xx: 401 у закрытого сайта или 404 у API без `/` — тоже ответ. Если задан `run.health`, проверяется он, и нужен успех — 2xx или 3xx. По этому правилу выкатка ждёт новую версию (иначе возвращает предыдущую), а проверка сайтов раз в минуту сообщает о простое. Адрес хранится у каждого релиза, поэтому при откате проверяется адрес из его `airlok.yml`.

Переменные окружения проект описывает в `airlok.yml` или в `.env.example` (`.env.sample`, `.env.template`); airlok.yml важнее:

```yaml
env:
  S3_BUCKET: Бакет Object Storage          # строка — описание обязательной переменной
  S3_SECRET_KEY: { secret: true }
  MAX_FILE_SIZE_MB: { default: "10" }      # со значением по умолчанию — необязательная
  SENTRY_DSN: { required: false, description: Ошибки в Sentry }
  SENTRY_AUTH_TOKEN: { secret: true, build: true }   # нужна и сборке
```

Список имён (`env: [OPENAI_API_KEY]`) по-прежнему значит «все обязательные». В `.env.example` пустое значение или заглушка (`your-key`, `changeme`, `<...>`) — обязательная переменная, заполненное — необязательная со значением по умолчанию, закомментированная строка — необязательная. Комментарий над строкой становится описанием; если в нём сказано «по умолчанию» или «необязательно», переменная тоже необязательна. `PORT`, `HOST`, `HOSTNAME`, `HOME` и `NODE_ENV` задаёт сам airlok.

Значения задаются на странице приложения в дашборде или командой `npx @airlok/cli env set ИМЯ --app <имя>`. Браузер и CLI шифруют их под ключ этого сервера (`/etc/airlok/env.key`: его создаёт агент, и сервер он не покидает), поэтому дашборд хранит только шифротекст и прочитать его не может. На выкатке и при перезапуске из дашборда агент расшифровывает их в `/srv/apps/<имя>/shared/panel.env`, поэтому новые значения доходят до приложения без пересборки — кроме переменных, которые встраиваются в код при сборке. Отпечаток ключа агент пишет в журнал при запуске (`journalctl -u airlok-agent | grep ключ`) — он должен совпадать с тем, что показывает дашборд. Значения можно вписать и прямо на сервере в `/srv/apps/<имя>/shared/user.env` (`ИМЯ=значение`, права 600); заданное в дашборде важнее. Если обязательной переменной нет ни там, ни там или она пустая, выкатка останавливается до сборки и перечисляет, что задать.

Сборка идёт в песочнице, где работают скрипты чужих пакетов, поэтому значения переменных она получает не все: только `NEXT_PUBLIC_*` и `VITE_*` (фреймворки встраивают их в код) и отмеченные в `airlok.yml` как `build: true`; `build: false` убирает из сборки и переменную с таким префиксом. Скрипты установки зависимостей их тоже видят — секрет отмечайте `build: true`, только если он правда нужен сборке. Готовый релиз того же коммита берётся без пересборки, только если переменные сборки с тех пор не менялись.

В монорепозитории (фронтенд и бэкенд в одном репозитории) приложение не в корне: рецепт назовёт подкаталоги, похожие на проекты, а выкатывать каждый нужно отдельным приложением со своим каталогом.

Миграции базы и задачи по расписанию задаются так же, как на хостинге:

```yaml
run:
  release: alembic upgrade head      # перед запуском каждой новой версии
capabilities:
  cron:
    - name: дайджест
      schedule: "0 9 * * 1-5"        # пять полей cron, время московское
      command: python digest.py
      timeout_min: 10                # от 1 до 60, по умолчанию 10
```

`run.release` выполняется после бэкапа базы и до запуска новой версии, один раз на сборку: повторная выкатка того же собранного релиза её не повторяет. Если команда не прошла или шла дольше 10 минут, новая версия не запускается, а прежняя продолжает работать.

Каждая задача из `capabilities.cron` — таймер systemd `airlok-cron@<имя>_<номер>.timer`. Задача идёт разовым контейнером приложения (`docker compose run`) с той же изоляцией, переменными и базой, на коде текущей версии, а во время выкатки ждёт её конца. Если прошлый запуск ещё идёт, следующий пропускается; дольше `timeout_min` задача не работает. Вывод с пометкой `[имя задачи]` и итог запуска уходят в логи приложения в дашборде, полный вывод — в `journalctl -u 'airlok-cron@<имя>_*'`. Запустить задачу сразу, не дожидаясь расписания: `sudo python3 /opt/airlok/recipes/cron.py run <имя>_<номер>` (номер — с нуля, по порядку в `airlok.yml`). Задачи, убранные из `airlok.yml`, выключает следующая выкатка. У статического сайта своего кода на сервере нет, поэтому ни `run.release`, ни задач у него быть не может.

## Установка

Одна команда ставит рецепты в `/opt/airlok`, готовит сервер (пакеты, Docker, nginx, ufw, fail2ban) и подключает его к дашборду. Её с токеном сервера показывает дашборд; повторный запуск обновляет рецепты и досоздаёт недостающее.

```bash
echo "ТОКЕН" | sudo bash -c "$(curl -fsSL https://airlok.ru/install.sh)" install https://app.airlok.ru
```

Без дашборда — то же без токена и адреса: `sudo bash -c "$(curl -fsSL https://airlok.ru/install.sh)"`.

Опции после адреса дашборда (их же собирает дашборд, когда вы отмечаете галочки):

| Опция | Что делает |
| --- | --- |
| `--letsencrypt [EMAIL]` | выпускать для сайтов настоящие сертификаты Let's Encrypt вместо самоподписанных; email — для писем о продлении, необязателен |
| `--ssh-keys-only` | последним шагом закрыть вход по паролю. Только если на сервере уже есть ваш SSH-ключ (у root или у того, кто запустил sudo), иначе пароль остаётся |

После `--ssh-keys-only` проверьте вход по ключу в **новом** окне и выполните `confirm-ssh`; если не подтвердить за 3 минуты, вход по паролю вернётся сам. Без опции пароль можно закрыть позже тем же способом:

```bash
sudo /opt/airlok/recipes/server-base.sh ssh
sudo /opt/airlok/recipes/server-base.sh confirm-ssh
```

`AIRLOK_REPO=…` перед командой берёт рецепты из зеркала или локального каталога вместо GitHub.

## Порядок вручную

```bash
cd /opt/airlok/recipes
sudo ./server-base.sh                 # один раз на сервер, вместе с SSH
sudo ./server-base.sh confirm-ssh     # после проверки входа по ключу в новом окне
sudo ./app-deploy.sh /путь/к/проекту  # деплой и каждая следующая выкатка
sudo ./app-restart.sh <имя>           # перезапуск той же версии без сборки
sudo ./app-remove.sh <имя>            # убрать с сервера; база, бэкапы и загрузки остаются
sudo ./app-remove.sh <имя> --with-data  # убрать вместе с данными, без возврата
sudo ./selftest.sh /путь/к/проекту    # проверка, что песочница работает как обещано
```

Повторный запуск любого шага безопасен.

## Деплой из GitHub

```bash
sudo ./github-deploy.sh setup  владелец/репозиторий           # ключ и инструкция, куда его добавить
sudo ./github-deploy.sh deploy владелец/репозиторий           # выкатить main
sudo ./github-deploy.sh deploy владелец/репозиторий a032b88   # выкатить конкретный коммит или ветку
sudo ./github-deploy.sh log    владелец/репозиторий           # последние коммиты
```

- У каждого репозитория свой deploy key. Добавлять его нужно **без** «Allow write access»: с таким ключом GitHub отклоняет push.
- Ключ хоста github.com зашит в скрипт и сверен с `api.github.com/meta`, поэтому подменить GitHub не получится.
- В релиз попадает только содержимое коммита (`git archive`), без `.git` и истории.
- Релиз называется по хешу коммита. Повторная выкатка уже собранного коммита не пересобирает его, поэтому откат занимает секунды: `deploy … <старый-хеш>`.

### Автоматическая выкатка по push

```bash
sudo ./github-deploy.sh webhook владелец/репозиторий [ветка]   # по умолчанию main
```

Команда печатает адрес и путь к секрету для GitHub: Settings → Webhooks → Add webhook, Content type `application/json`, событие push. Если приложение уже было развёрнуто раньше, выкатите его один раз: так в конфиг nginx добавится адрес webhook.

Как устроено:
- приёмник (`webhook.py`) работает от отдельного пользователя `airlok-hook` в изолированной службе systemd. Он проверяет подпись `X-Hub-Signature-256` до того, как читает содержимое запроса, и только ставит «репозиторий + коммит» в очередь. Ни deploy key, ни прав на деплой у него нет;
- очередь разбирает служба от root (`airlok-deploy-queue`) и ещё раз проверяет оба значения;
- выкатывается только push в выбранную ветку. Если во время выкатки пришло несколько push, следующей выкатится последняя версия;
- журнал: `journalctl -u airlok-webhook -u airlok-deploy-queue`.

## Уведомления в Telegram

```bash
sudo ./notify.sh setup   # подключить своего бота, запускать в терминале
sudo ./notify.sh test    # пробное сообщение
```

`setup` попросит создать бота у @BotFather, скрытно спросит токен и сам найдёт ваш чат по сообщению, которое вы отправите боту. Токен хранится только на сервере в `/etc/airlok/telegram.env` с правами 600 и не попадает в аргументы процессов.

Что приходит:
- ✅ версия выкачена: какой коммит и за сколько секунд;
- ⚠️ новая версия не поднялась, вернули предыдущую;
- ❌ выкатка не удалась или не началась, с причиной;
- 🔴 сайт не отвечает две проверки подряд, с причиной: контейнер остановлен, не хватило памяти, приложение падает по кругу, nginx не работает, заполнен диск;
- ✅ сайт снова отвечает, с длительностью простоя.

Сайт проверяется каждую минуту (`airlok-healthcheck.timer`). Сообщение приходит только при смене состояния, а не каждую минуту, пока сайт лежит. Во время выкатки проверка пропускается. Проверка идёт с самого сервера, поэтому если сервер выключился целиком, сообщить он не сможет.

## Дашборд

```bash
echo "airlok_srv_…" | sudo ./notify.sh dashboard https://dash.example.ru
```

Токен агента выдаёт дашборд при добавлении сервера. Команда проверяет адрес и токен (`/agent/v1/ping`) и только потом сохраняет их в `/etc/airlok/dashboard.env` с правами 600. После этого в дашборд уходят те же события, что и в Telegram: итог каждой выкатки и смена доступности сайта, а при первой проверке — его начальный статус. Раз в минуту сервер сообщает своё состояние: память, диск, нагрузку, открыт ли вход по паролю, включён ли Let's Encrypt.

### Выкатка кнопкой из дашборда

Вместе с подключением ставится служба `airlok-agent`. Она сама ходит в дашборд долгим опросом и забирает команды — входящих соединений сервер не принимает. Агент умеет выкатить указанный коммит репозитория GitHub, перезапустить выкаченное приложение без сборки (`app-restart.sh`), убрать его с сервера (`app-remove.sh`, данные — только если человек отметил это в дашборде), прочитать данные его базы и обновиться сам, когда это подтвердил человек. Произвольную команду дашборд прислать не может, а каждое поле команды (имя приложения, репозиторий, хеш коммита, ветка, каталог, свой домен) агент проверяет заново.

- Закрытый репозиторий агент забирает по HTTPS с токеном GitHub App, который дашборд выдаёт на одну выкатку: только чтение, только этот репозиторий, живёт час. Токен передаётся git через переменные окружения и не попадает ни в аргументы процессов, ни в логи, ни на диск. Публичный репозиторий забирается без токена.
- В монорепозитории фронтенд и бэкенд — отдельные приложения: у каждого свой каталог проекта и своё имя на сервере, которое задаёт дашборд.
- Команды выполняются по одной. Пока идёт выкатка, агент раз в несколько секунд отправляет в дашборд хвост вывода и этапы (код, сборка, запуск, сайт), в конце — итог. Последний вывод лежит в `/var/lib/airlok/agent/command.log`.
- Журнал: `journalctl -u airlok-agent`. Обновлённые рецепты агент подхватывает сам между командами.

### Логи приложений в дашборде

Вместе с агентом ставится служба `airlok-logs` (`recipes/logs.py`). Она читает вывод контейнеров приложений через `docker logs` (stdout и stderr по отдельности; у служб кроме `app`, например базы, строка помечена `[db]`) и отправляет его в дашборд: там он хранится неделю, до 20 000 строк на приложение. Собираются только приложения, у которых в дашборде включены логи. У новых приложений они включены сразу, у выкаченных до этой версии их нужно включить в настройках.

- Пока логи приложения открыты в дашборде, строки уходят каждые 200 мс, иначе — раз в 5 секунд.
- Больше 200 строк в секунду от одного приложения не отправляется: лишнее отбрасывается, а в логи приходит строка о том, сколько пропущено.
- Пока дашборд недоступен, строки ждут в памяти до 5 МБ, дальше выбрасываются самые старые. Где остановилась в каждом контейнере, служба помнит в `/var/lib/airlok/logs/state.json`, поэтому после перезапуска строки не повторяются.
- Вывод задач по расписанию и команды перед запуском `cron.py` кладёт в очередь `/var/lib/airlok/logs/spool`: разовый контейнер живёт секунды и исчезает раньше, чем служба его заметит.
- Журнал: `journalctl -u airlok-logs`. Полный вывод по-прежнему на сервере: `docker compose -f /srv/apps/<имя>/compose.yml logs app`.

### Обновление агента

Сам агент не обновляется: о новой версии сообщает дашборд, а обновить можно все серверы или выбранные, нажав кнопку. По этой команде агент запускает `update.sh`: забирает новую версию в `/opt/airlok` (`git pull --ff-only`), повторяет базовую настройку сервера, чтобы досоздать то, что появилось в новой версии, обновляет службы, сообщает итог и перезапускается. У команды нет параметров: обновиться агент может только из своего репозитория.

Если в `/opt/airlok` есть локальные правки, обновление остановится и покажет причину. То же самое вручную:

```bash
sudo /opt/airlok/recipes/update.sh
```

Агент версии раньше 26.10.2026 команду обновления не знает: его один раз обновляют вручную командой, которую покажет дашборд.

### База в дашборде

Вкладка «База» и инструмент MCP `query_database` читают Postgres приложения через агента (`recipes/dbquery.py`). Агент подключается к контейнеру базы от роли `airlok_ro`: она может только читать (`pg_read_all_data`) и не суперпользователь, поэтому ни изменить данные, ни выполнить команду в системе через неё нельзя. Каждый запрос — один оператор в транзакции только на чтение, до 5 секунд, и строк база отдаёт не больше, чем просили. Роль заводится при первом запросе, её пароль — в `/srv/apps/<имя>/shared/db-ro.env`. Агент выполняет команды по очереди, поэтому пока идёт выкатка, запрос ждёт её конца.

### Метрики

nginx пишет для каждого сайта отдельный лог `/var/log/nginx/airlok-<имя>.access.log` в коротком формате: время, код ответа, длительность и размер. IP посетителей и адреса страниц не пишутся. Раз в минуту `metrics.py` считает по законченным минутам число запросов, ошибки 4xx и 5xx, объём и время ответа (медиана и 95-й перцентиль) и отправляет в дашборд. Если дашборд недоступен, минуты копятся в `/var/lib/airlok/metrics` до 7 дней.

События сначала записываются в очередь `/var/lib/airlok/events` (права 700) и уже потом отправляются, поэтому недоступность дашборда их не теряет:
- очередь отправляется по порядку сразу после нового события и ещё раз каждую минуту вместе с проверкой сайтов;
- если нет связи, дашборд отвечает ошибкой, просит подождать или не принимает токен, событие остаётся в очереди до следующей попытки;
- если дашборд отверг само событие (400 или 413), оно перекладывается в `failed/`, чтобы не задерживать остальные;
- у каждого события есть `id` и время. Повтор не задваивает историю, в ней показывается время события, а не время доставки, а более старое событие не перетирает более новый статус сайта;
- в очереди хранится до 1000 событий, в `failed/` — до 100, самые старые удаляются.

Выкатка и проверки от доступности дашборда не зависят.

Пока сертификат самоподписанный, в настройках webhook GitHub приходится отключать проверку SSL. Подпись запроса это не ослабляет, но для настоящего домена выпустите сертификат и включите проверку обратно.

## Let's Encrypt

```bash
sudo ./server-base.sh letsencrypt [email]   # или опция --letsencrypt установщика
```

Ставит certbot и включает выпуск: сертификат для домена приложения выпускается при выкатке через webroot (`/.well-known/acme-challenge/` на 80-м порту) и продлевается сам (`certbot.timer`, после продления nginx перечитывает конфиг). A-запись домена должна указывать на сервер. Если выпустить не вышло, выкатка не падает: сайт работает с самоподписанным сертификатом, а следующая выкатка попробует снова. Причина — в `/srv/apps/<имя>/shared/letsencrypt.log`.

## Что делает каждый шаг

**server-base.sh**
- автообновления безопасности, swap;
- Docker с ротацией логов и `no-new-privileges`;
- ufw: открыты SSH, 80 и 443;
- fail2ban, nginx без версии в заголовках;
- вход по SSH только по ключу. Если не выполнить `confirm-ssh` за 3 минуты, настройка SSH откатится сама, так что доступ к серверу не потеряется.

**app-deploy.sh**
- не выкатывает, если домен из манифеста уже занят другим сайтом на сервере: иначе nginx молча отдавал бы его старому сайту;
- отдельный пользователь Linux для приложения, без входа и sudo;
- код принадлежит root и смонтирован в контейнер только на чтение;
- сборка в отдельном контейнере без секретов и доступа к базе;
- контейнер приложения: файловая система только на чтение, без привилегий, порт только на `127.0.0.1`, лимиты памяти и процессов;
- загрузки — единственная папка с записью, смонтирована с `noexec`;
- nginx отдаёт из загрузок только разрешённые расширения, с `nosniff` и CSP sandbox, не картинки — только на скачивание;
- Postgres без опубликованных портов, ежедневный дамп и дамп перед каждой выкаткой;
- команда перед запуском и задачи по расписанию — в разовых контейнерах приложения с теми же ограничениями;
- если новая версия не ответила за 2 минуты, возвращается предыдущая.

**selftest.sh** проверяет всё перечисленное изнутри контейнера, на сервере и через nginx.

## Где что лежит

| Путь | Что |
| --- | --- |
| `/srv/apps/<имя>/releases/` | релизы, `current` — активный |
| `/srv/apps/<имя>/shared/uploads/` | загрузки пользователей |
| `/srv/apps/<имя>/shared/user.env` | ваши секреты (`OPENAI_API_KEY=…`), права 600 |
| `/srv/apps/<имя>/shared/panel.domain` | свой домен из дашборда, который прислал агент; по нему идут и выкатки без агента |
| `/srv/apps/<имя>/shared/panel.env` | переменные из дашборда, расшифрованные агентом; заменяется на каждой выкатке и перезапуске из дашборда |
| `/etc/airlok/env.key` | закрытый ключ, под который дашборд шифрует переменные; сервер не покидает |
| `/srv/apps/<имя>/shared/backups/` | дампы базы, 7 последних |
| `/srv/apps/<имя>/shared/cron.json` | задачи по расписанию выкаченной версии; таймеры — `/etc/systemd/system/airlok-cron@<имя>_*.timer` |
| `/srv/apps/<имя>/shared/released` | релиз, для которого `run.release` уже выполнена |
| `/srv/apps/<имя>/shared/db-ro.env` | пароль роли `airlok_ro`, от которой дашборд читает базу; права 600 |
| `/etc/nginx/sites-available/airlok-<имя>.conf` | конфиг сайта |
| `/var/log/nginx/airlok-<имя>.access.log` | лог запросов для метрик |
| `/etc/airlok/server.env` | настройки сервера: Let's Encrypt |
| `/etc/airlok/dashboard.env` | адрес дашборда и токен агента, права 600 |

## Чего пока нет

- `outbound_network: false` описан в формате манифеста, но рецепт его пока не поддерживает и честно останавливается.
- Без `--letsencrypt` сертификат самоподписанный.
- Бэкапы лежат на том же сервере.
- Внешней проверки доступности (с другого сервера) пока нет.
- Подмодули git не поддерживаются.
